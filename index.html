Anomaly Detection Benchmarking Platform & Dashboard

My graduation project at deZem GmbH (Berlin): a full-stack benchmarking platform that compares anomaly detection models against each other on real energy time series. A Rust execution engine, a FastAPI backend and a React/TypeScript dashboard, deployed as a five-service Docker stack. It produced deZem's first systematic three-model comparison on real energy data.

React / TypeScriptRust FastAPIPyTorch Docker

The problem

Choosing an anomaly detection model for energy time series had no systematic, reproducible way to compare candidates. Evaluating a model on a new dataset meant hand-crafting an API request, parsing the JSON response by hand and computing metrics in a one-off notebook.

That workflow was slow, hard to reproduce, and didn't scale: comparing several datasets across parameter combinations meant many manual API calls and error-prone metric aggregation, with no dataset management layer underneath.

What I built

  • A Rust CLI execution engine running models concurrently against a shared dataset pool
  • A FastAPI backend for dataset management, run orchestration and persistent run history
  • A React/TypeScript dashboard with four tabs, time series visualisation with anomaly overlays, cross-run comparison charts, and CSV/PDF export
  • Each model wrapped as an independent service, so new models plug in behind a common API contract

The comparison it produced

Three models on the same steam-flow test data, 148 anomalies across 5,934 points:

ModelPrecisionRecallF1Speed
Statistical baseline0.6540.5740.612~3s
Mamba AE0.6170.8720.723~73s
Transformer AE0.4030.6490.497~1.8s

How far to read this: one dataset, one run. Each model also reads the data in differently sized windows, so the timings and the scores are not a perfectly like-for-like comparison. It is enough to tell the models apart by character, not enough to crown a winner in general.

What it revealed

  • No single model wins, which is exactly what the platform was built to show. Mamba catches the most anomalies, so it suits cases where missing one is costly. The statistical baseline raises the fewest false alarms. The Transformer is much faster than Mamba while still catching a reasonable share
  • Preparation matters as much as architecture. Fine-tuning took Mamba from the weakest model to the strongest on this dataset
  • Threshold calibration alone lifted the Transformer's F1 from 0.365 to 0.497, with no retraining. A tuning decision, not a modelling one, bought a 36% improvement

Impact

A manual, ad-hoc process became a reproducible platform, and the resulting comparison gave deZem an evidence-based answer to "which model should we run?" per operational priority rather than by assumption. It was built to serve both internal engineering teams and deZem's clients benchmarking models on their own sensor data.

What I'd add next

Authentication and role-based access before client rollout, automated regression tests, and broader sensor coverage beyond steam-flow (electricity, temperature, pressure).

Mamba Autoencoder: Anomaly Detection Fine-Tuning

Fine-tuned a Mamba-based autoencoder for time-series anomaly detection, adapting the data pipeline, scoring logic and serving API to match the organization's real IoT sensor data, then retrained and re-evaluated the model.

0.72F1 on real data
0.87Recall
0.62Precision
PythonMamba / SSM PyTorchFastAPI

The problem

Labelled anomalies barely exist in real IoT data, so you can't train a classifier on failures you've never seen. So the model learns only what normal looks like and flags whatever it can't reconstruct through its bottleneck.

What I did

  • Adapted the data pipeline, scoring logic and serving API to the organization's real sensor data
  • Retrained and re-evaluated against the SMD (Machine-1-1) benchmark
  • Tuned the reconstruction-error threshold at the 99th percentile of training error

Results on the real sensor data

On the steam-flow dataset the model was actually built for, the fine-tuned version reached F1 0.723, with recall 0.872 and precision 0.617. It caught roughly seven anomalies in eight while keeping false alarms at a level an operator can live with, and it was the strongest of the three models in the benchmarking platform above.

What the public benchmark showed

On SMD (Machine-1-1), a standard public dataset, the picture was very different: ROC-AUC 0.9274, but F1 only 0.35. Recall came out at 1.00 there, which sounds ideal and isn't: precision works out at roughly 0.21, so about four in five alerts were false alarms. A model that flags almost everything also scores a perfect recall, which is why that number means little on its own.

Where those false positives come from: I traced them to a regime change in the test set. The machine's normal operating behaviour shifts partway through, so the model correctly reports "this isn't what I was trained on" and gets scored as wrong. That points to a drift problem rather than a detection one, though it stays a hypothesis until the threshold is re-fitted on the post-shift regime and the precision recovers.

Why both numbers are here

The same model scores well on one dataset and poorly on another, and that gap is the useful part. It is consistent with the drift reading rather than proof of it, since the two runs differ in dataset, domain and threshold percentile. What it does show is that a single benchmark number says little about how a detector will behave on the data you actually care about.

What I'd do next

Periodic retraining or an adaptive threshold that tracks the operating regime, so precision recovers without giving up the recall.

Transformer Autoencoder: Anomaly Detection Training

Built the training pipeline and serving API for a transformer-based anomaly detection autoencoder, then tuned it on benchmark datasets to improve detection on real sensor data.

6Model configs
3Threshold methods
2Architectures
PythonTransformers PyTorchFastAPI

The problem

There's no single right anomaly detector for every sensor. Rather than ship one fixed model, I built a training pipeline where the architecture, the model size and the thresholding strategy are all configurable, so the model can be matched to the data instead of the other way round.

The design decisions

  • Two architectures: a lightweight one that compresses the signal through a small bottleneck, and a fuller encoder-decoder version. The lightweight one gives up some accuracy for speed, which matters when the model has to run on limited hardware
  • Three sizes (pico, medium, ookii) for each, so six setups in total. A small sensor doesn't need a large model, and this makes that choice explicit
  • Trained models can also be reused as feature extractors, so the patterns they learn aren't locked inside one detector

The part that actually decides performance

In unsupervised detection, the threshold matters as much as the model, since it's what converts a reconstruction error into an alert. I implemented three strategies:

  • Gaussian (the default): alert when the error goes more than 3 standard deviations above the training average. Simple and stable when errors are evenly spread
  • POT: models the extreme errors directly. More work, but it holds up better when a few very large errors would skew the simple average
  • Percentile (top 5%): blunt, but predictable, and useful as a baseline to compare the other two against

Why it was built this way

Making these swappable turns "which model is best?" into something you can measure per sensor, which is exactly what fed into the benchmarking platform above.

KPI Sales & Customer Dashboard

A 3-page Power BI report covering Executive, Product and Regional & Customer views: KPI cards for total sales, orders, customer count, YoY growth and sales YTD, a sales-over-time trend, sales by month per country, a product-level breakdown, and customer distribution by country.

8KOrders
3KCustomers
3Report pages
Power BIDAX

The problem

An online gift retailer's transaction log covering Apr 2010 to Dec 2011: roughly 8K orders from 3K customers across ~30 countries. Useful at the row level, unreadable at the business level. The question was what a decision-maker should actually look at first.

How I structured it

Three pages, each answering a different person's question rather than one page showing everything:

  • Executive: the headline position, with total sales, year-to-date and prior-year KPI cards, a sales-over-time trend and sales by month per country
  • Product: drills into a single item, with average price, average basket and its own sales trend
  • Regional & Customer: filters by country to expose who buys what and where

What the data shows

  • Activity is heavily concentrated in 2011. Sales-over-time runs as a smooth, modest line through 2010, then becomes high-frequency and far more volatile through 2011
  • Volatility is the story, not the average. Sharp spikes against a low baseline point to bulk or seasonal ordering rather than steady demand, a wholesale-style pattern, which changes how you'd forecast it
  • Breadth beats depth per product. On the product page, top items reach only ~10 distinct customers each, so revenue rests on a wide catalogue of small buyer groups, not a few bestsellers

Reading the YoY figure correctly: the card shows 9.27, but dividing year-to-date sales by prior-year sales returns exactly that number, so the measure is producing a ratio, not a percentage. Quoting it as "9.27% growth" would understate it by orders of magnitude. It also compares a full 2011 against a partial 2010 starting in April, so part of the gap is coverage rather than performance. My next iteration would normalise the comparison to matching periods and format the measure explicitly as a percentage.

DAX worth noting

Time-intelligence measures for year-to-date and prior-year sales over a proper date table, so the YoY comparison stays correct as slicers change. The same measure has to hold up when a user filters to Belgium or to one product.

Data Cleaning in SQL

Took a messy, real-world layoffs dataset and made it analysis-ready: removed duplicates, standardized inconsistent text, fixed date formatting, recovered missing values where possible, and dropped rows with no usable information.

2,361Rows in
1,995Analysis-ready
0Duplicates left
SQL

The problem

A raw layoffs dataset of 2,361 rows that couldn't be trusted for analysis: duplicate events would double-count, the same industry appeared under three different names, and dates were stored as text so no time-series query would work.

How I approached it

  • Never touched the raw table. All work happened on a staging copy, so the import stays reproducible and the lineage is intact
  • Duplicates: ROW_NUMBER() partitioned across every column to catch true duplicates, which found and removed 5
  • Standardization: trimmed company whitespace, merged 3 "Crypto" spellings into one, stripped trailing periods from country names
  • Dates: converted text to a real DATE type with STR_TO_DATE()
  • Missing values: recovered blank industries via a self-join on company name, rather than guessing or dropping them

The judgement call

Rows missing both the total and the percentage laid off carry no analytical signal, so I deleted them. That's the bulk of the drop from 2,356 to 1,995, a deliberate choice to lose volume in exchange for a dataset where every row can actually answer a question.

Why it mattered

Those 3 "Crypto" variants alone would have split one industry into three and buried it in the rankings. This cleanup is what makes the EDA project's findings trustworthy.

Exploratory Data Analysis in SQL

Queried the cleaned dataset to answer real business questions: which companies and industries were hit hardest, how layoffs trended year over year, and which companies led each year, using window functions and rolling totals.

18,150Largest cut
10×2021→2022 jump
4 yrsTrend covered
SQL

The questions I set out to answer

Who was hit hardest, was this an industry story or a company story, and was the downturn accelerating or easing?

What I found

  • Layoffs came in rounds, not one event. Amazon's 18,150 is a sum across multiple rounds, while Google's 12,000 and Meta's 11,000 were single cuts. Aggregating per company instead of per row is what surfaces that difference
  • 2022 was the shock year. ~81k in 2020 → ~16k in 2021 → ~161k in 2022, roughly a tenfold jump, then ~126k in 2023 by the data's cutoff
  • Consumer and Retail led, ahead of Transportation and Finance. Read carefully, that ranking is about which verticals within tech were hit hardest, not the retail sector at large
  • Some companies shut down entirely. Filtering on percentage_laid_off = 1 separates full closures from cost-cutting, two very different signals

Techniques worth noting

  • A rolling monthly total via a window function, so the trend reads as cumulative build-up rather than noisy month-to-month spikes
  • DENSE_RANK() for the top 3 companies per year, chosen over ROW_NUMBER() so genuine ties share a rank instead of being broken arbitrarily
  • Cross-cutting the data by funding stage, revealing whether mature Post-IPO firms or earlier-stage companies drove the volume

The caveats I'd flag to a stakeholder

  • 2023 is a partial year, stopping at the dataset's cutoff. Reading it as a year-over-year decline from 2022 would be wrong
  • This is a tech and startup sample, not the whole economy. Every company in it is tracked because it's venture-backed or tech-adjacent, so the industry labels describe verticals inside that world. Nothing here supports a claim about layoffs economy-wide, and the totals are floors rather than true counts, since only reported events appear
